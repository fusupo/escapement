# Manifest System V2: Dependency-First Parallel Work Orchestration

> Revised design for a manifest that models work dependencies, predicts file overlap, and coordinates parallel agent execution without duplicating Escapement's existing archive system.
>
> Captured: 2026-03-31
> Status: Design phase
> Replaces: `docs/MANIFEST_SYSTEM_DESIGN.md` as the preferred starting point for implementation

---

## 1. Why V2

V1 identified the right problem: Escapement can orchestrate more than one issue at a time, but it lacks a persistent dependency model for deciding what is safe to run in parallel.

V1 also over-modeled several things:

- It stored logical inverses such as `depends_on` and `unlocks`
- It stored both file arrays and file triples
- It modeled archive provenance as both a path on the work item and a separate archive entity
- It treated conflict classification as durable graph truth, even though that classification is often provisional

V2 keeps the same intent but reduces the number of canonical truths.

The key design change is simple:

- The manifest is primarily a dependency graph over work items
- File overlap is planning data, not core graph structure
- Archive provenance is owned by Escapement's context-path system and referenced by the manifest, not re-modeled inside it

---

## 2. Design Goals

1. Represent the dependency topology of planned and active work
2. Identify which work items are dispatchable right now
3. Predict file overlap well enough to support cautious parallel execution
4. Preserve provenance back to Escapement archives and session logs
5. Stay simple enough to rebuild during MVP without migrations becoming the main project

## 3. Non-Goals

1. Perfectly predict code changes from issue text alone
2. Model every file as a first-class graph node in MVP
3. Persist every planner inference as durable schema
4. Replace Escapement's existing `archive-work`, `stash-artifact`, or `INDEX.md` behavior

---

## 4. Ground Truth and Assumptions

### 4.1 Bootstrap Scope

Bootstrap is allowed to read broadly:

- the target repo codebase
- relevant design docs
- the full open issue set, even when that is 50+ issues

The large context window makes this feasible, but bootstrap should still include an explicit pruning pass:

1. ingest candidate issues
2. classify each as `active`, `deferred`, `stale`, or `unclear`
3. ask the user to confirm removals or deferrals before seeding the manifest

The point is not to avoid reading stale issues. The point is to make staleness visible early instead of silently polluting the graph.

### 4.2 Conflict Classification Is Probabilistic

At bootstrap time, the agent can inspect both issue text and the codebase, and that should produce useful file predictions. But overlap classification remains an estimate until implementation begins.

V2 therefore distinguishes between:

- durable facts: dependencies, hierarchy, issue links, predicted file sets
- planner judgments: `trivial`, `additive`, `semantic`, `unknown`

Planner judgments may be persisted as notes in `meta`, but they are not treated as primary graph edges.

### 4.3 GitHub Write-Back Is Intentional

Disambiguation work is valuable enough to propagate back to GitHub issues. V2 keeps that behavior, but the write step should remain explicit:

- default bootstrap/check behavior may prepare write-back payloads
- actual issue comments or body edits require user confirmation or an explicit `--writeback` mode

### 4.4 MVP Persistence Model

For MVP, the manifest lives in the project's Escapement context-path and is allowed to be disposable. Re-bootstrap is a supported operation.

That implies:

- migrations are low priority in MVP
- SQL export/import is sufficient for recovery
- schema design should optimize for clarity and rebuildability, not long-lived backward compatibility

### 4.5 Practical Parallelism

Parallelism is constrained more by validation cost than by editing cost.

V2 assumes:

- multiple agents may analyze and edit in parallel
- Node-heavy builds/tests must be rate-limited or serialized
- dispatch planning should emit both editing groups and validation constraints

The system's value does not depend on fully parallel test execution. It depends on avoiding unnecessary serialization of analysis and coding work.

## 5. Relationship to Existing Escapement Archive Behavior

Escapement already has a concrete archive model:

- branch-scoped directories under `{context-path}/{branch}/`
- archived work at `{context-path}/{branch}/archive/`
- optional supporting artifacts under `notes/` and `scripts/`
- a root `{context-path}/INDEX.md` maintained by `archive-work`
- per-archive `README.md` files generated by `archive-work`

This matters because archive provenance is already structured outside the manifest.

### 5.1 Archive Review

The broader Escapement plugin suggests three design constraints:

1. The archive directory path is already the stable provenance handle in practice.
2. `archive-work` already writes summary metadata to `README.md` and a root `INDEX.md`.
3. The manifest should not become a second archive registry.

### 5.2 Consequence for V2

V2 does **not** model archive directories as graph entities in MVP.

Instead:

- each completed work item stores `archive_path`
- the archive directory remains owned by `archive-work`
- provenance queries use the stored path and, when needed, read `README.md` or `INDEX.md`

This is simpler and better aligned with the plugin that already exists.

### 5.3 Existing Archive Inconsistency

Escapement's current docs are slightly inconsistent about `INDEX.md` ordering:

- `skills/archive-work/SKILL.md` and `README.md` describe chronological oldest-first append order
- `docs/CONTEXT_PATH.md` still describes newest-first

V2 assumes the skill is canonical because it is the operational workflow definition. That documentation mismatch should be reconciled separately, but it does not block the manifest design.

## 7. Canonical Data Model

### 7.1 Design Principle

Only store data that the system cannot cheaply derive at query time.

Canonical truths in V2:

- work item identity
- work item state
- dependency edges
- hierarchy edges
- capability-to-issue linkage
- predicted file sets
- actual file sets
- archive path

Derived or planner-only data in V2:

- `unlocks`
- `conflicts_with`
- `parallel_safe_with`
- archive graph entities

### 7.2 Schema

```sql
CREATE TABLE work_items (
    id              TEXT PRIMARY KEY,
    name            TEXT NOT NULL,
    kind            TEXT NOT NULL
                    CHECK (kind IN (
                      'issue',
                      'capability',
                      'phase',
                      'track'
                    )),
    state           TEXT NOT NULL DEFAULT 'planned'
                    CHECK (state IN (
                      'planned',
                      'in_progress',
                      'done',
                      'deferred',
                      'cancelled'
                    )),
    repo            TEXT,
    issue_number    INTEGER,
    issue_url       TEXT,
    scope_hint      TEXT,
    branch          TEXT,
    archive_path    TEXT,
    predicted_files TEXT[] DEFAULT '{}',
    actual_files    TEXT[] DEFAULT '{}',
    meta            JSONB NOT NULL DEFAULT '{}',
    updated_at      TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE edges (
    id          SERIAL PRIMARY KEY,
    from_id     TEXT NOT NULL REFERENCES work_items(id),
    rel         TEXT NOT NULL
                CHECK (rel IN (
                  'depends_on',
                  'is_part_of',
                  'implemented_by'
                )),
    to_id       TEXT NOT NULL REFERENCES work_items(id),
    confidence  TEXT NOT NULL DEFAULT 'certain'
                CHECK (confidence IN ('certain', 'inferred', 'ambiguous')),
    meta        JSONB NOT NULL DEFAULT '{}',
    created_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
    UNIQUE (from_id, rel, to_id)
);

CREATE INDEX idx_work_items_kind ON work_items(kind);
CREATE INDEX idx_work_items_state ON work_items(state);
CREATE INDEX idx_work_items_repo ON work_items(repo);
CREATE INDEX idx_work_items_predicted_files ON work_items USING gin(predicted_files);
CREATE INDEX idx_work_items_actual_files ON work_items USING gin(actual_files);
CREATE INDEX idx_edges_rel ON edges(rel);
CREATE INDEX idx_edges_from_id ON edges(from_id);
CREATE INDEX idx_edges_to_id ON edges(to_id);
CREATE INDEX idx_edges_confidence ON edges(confidence);
```

### 7.3 State Semantics

`state` is execution state, not manifest membership.

That means:

- `planned`: known to the manifest, not yet started
- `in_progress`: currently being worked
- `done`: completed and synced
- `deferred`: intentionally excluded from current planning horizon
- `cancelled`: no longer relevant

Dispatchability is derived from `state`, dependencies, and ambiguity metadata. It is not stored as a column.

### 7.4 Metadata Conventions

`meta` should hold uncertain or auxiliary information without changing the core graph.

Example:

```json
{
  "bootstrap_status": "active",
  "needs_human": false,
  "ambiguities": [],
  "conflict_notes": [
    {
      "other": "sr#587",
      "shared_files": ["packages/viewfinder/src/hooks/useClarity2Modelling.ts"],
      "assessment": "additive",
      "confidence": "inferred",
      "reason": "same pattern, different switch arm"
    }
  ],
  "writeback": {
    "last_prepared_at": "2026-03-31T10:15:00Z",
    "last_applied_at": null
  }
}
```

## 9. Core Queries

### 9.1 Frontier Query

Dispatchable items are planned work items with no unmet dependencies and no unresolved human gate.

```sql
SELECT w.id, w.name, w.kind, w.repo, w.scope_hint, w.predicted_files
FROM work_items w
WHERE w.kind IN ('issue', 'capability')
  AND w.state = 'planned'
  AND COALESCE((w.meta->>'needs_human')::boolean, false) = false
  AND NOT EXISTS (
    SELECT 1
    FROM edges e
    JOIN work_items dep ON dep.id = e.to_id
    WHERE e.rel = 'depends_on'
      AND e.from_id = w.id
      AND dep.state != 'done'
  );
```

### 9.2 File Overlap Discovery

This discovers potential contention without persisting it as graph structure.

```sql
WITH frontier AS (
  SELECT id, predicted_files
  FROM work_items
  WHERE kind IN ('issue', 'capability')
    AND state = 'planned'
    AND predicted_files <> '{}'
    AND COALESCE((meta->>'needs_human')::boolean, false) = false
    AND NOT EXISTS (
      SELECT 1
      FROM edges e
      JOIN work_items dep ON dep.id = e.to_id
      WHERE e.rel = 'depends_on'
        AND e.from_id = work_items.id
        AND dep.state != 'done'
    )
)
SELECT
  a.id AS node_a,
  b.id AS node_b,
  ARRAY(
    SELECT shared_file
    FROM (
      SELECT unnest(a.predicted_files) AS shared_file
      INTERSECT
      SELECT unnest(b.predicted_files) AS shared_file
    ) s
    ORDER BY shared_file
  ) AS shared_files
FROM frontier a
JOIN frontier b ON a.id < b.id
WHERE a.predicted_files && b.predicted_files;
```

### 9.3 Dependency Inspection

```sql
SELECT blocker.id, blocker.name, blocker.state
FROM edges e
JOIN work_items blocker ON blocker.id = e.to_id
WHERE e.rel = 'depends_on'
  AND e.from_id = $1
ORDER BY blocker.id;
```

### 9.4 Hierarchical Progress

Progress should account for nested tracks under phases. Use a recursive rollup instead of the V1 direct-child query.

```sql
WITH RECURSIVE tree AS (
  SELECT
    parent.id AS root_id,
    child.id  AS child_id
  FROM work_items parent
  JOIN edges e ON e.to_id = parent.id AND e.rel = 'is_part_of'
  JOIN work_items child ON child.id = e.from_id
  WHERE parent.kind IN ('phase', 'track')

  UNION ALL

  SELECT
    tree.root_id,
    child.id
  FROM tree
  JOIN edges e ON e.to_id = tree.child_id AND e.rel = 'is_part_of'
  JOIN work_items child ON child.id = e.from_id
)
SELECT
  root.name,
  COUNT(*) FILTER (WHERE leaf.kind IN ('issue', 'capability')) AS total_items,
  COUNT(*) FILTER (
    WHERE leaf.kind IN ('issue', 'capability') AND leaf.state = 'done'
  ) AS done_items
FROM tree
JOIN work_items root ON root.id = tree.root_id
JOIN work_items leaf ON leaf.id = tree.child_id
GROUP BY root.id, root.name
ORDER BY root.name;
```

### 9.5 Provenance Query

```sql
SELECT id, name, branch, archive_path
FROM work_items
WHERE id = $1
  AND archive_path IS NOT NULL;
```

If richer provenance is needed, the caller reads:

- `{archive_path}/README.md`
- `{context-path}/INDEX.md`

## 10. Bootstrap Workflow

### 10.1 Cold Start

Trigger:

- "build a manifest"
- "bootstrap the issue graph"
- first use on a repo with no manifest

### 10.2 Bootstrap Stages

1. Read relevant design docs for phase and track structure.
2. Read the open issue corpus.
3. Classify issues into:
   - `active`
   - `deferred`
   - `stale`
   - `unclear`
4. Ask the user to confirm any removals or deferrals.
5. Seed phases and tracks.
6. Create issue and capability work items.
7. Infer `depends_on`, `is_part_of`, and `implemented_by` edges.
8. Predict file sets for each active issue.
9. Mark unresolved scope or dependency questions in `meta.ambiguities`.
10. Prepare optional GitHub write-back payloads.

### 10.3 Ambiguity Handling

Ambiguities should be structured and minimal.

Example:

```text
I need decisions for 3 items before the frontier is reliable:

1. sr#589: occurrence form
   Question: hard dependency on sr#598 REST routes, or can it ship over WS?

2. sr#632: defensive deployment
   Question: which packages/files are in scope?

3. sr#640: deprecate construct
   Question: active for this phase, or defer behind current form hardening work?
```

Resolved ambiguities update:

- `edges.confidence`
- `work_items.meta.needs_human`
- `work_items.meta.ambiguities`

### 10.4 GitHub Write-Back

Bootstrap may prepare a write-back block for each clarified issue:

- dependency clarification
- predicted scope
- overlap notes

Applying that write-back is a separate explicit step. This preserves trust while still capturing the value of the analysis.

## 11. Dispatch Planning

### 11.1 Planner Inputs

The planner reads:

- frontier work items
- file overlap results
- ambiguity flags
- repo boundaries
- resource limits

### 11.2 Planner Output

```typescript
interface DispatchPlan {
  generated_at: string;
  assumptions: string[];
  parallel_groups: ParallelGroup[];
  sequential: SequentialNode[];
  validation_policy: {
    max_concurrent_node_heavy_tasks: number;
    serialized_checks: string[];
  };
  summary: {
    frontier_count: number;
    dispatchable_now: number;
    blocked_count: number;
    human_gate_count: number;
  };
}

interface ParallelGroup {
  repo: string;
  nodes: {
    id: string;
    name: string;
    branch: string;
    files_owned: string[];
    files_shared: {
      path: string;
      assessment: 'trivial' | 'additive' | 'semantic' | 'unknown';
      confidence: 'certain' | 'inferred' | 'ambiguous';
      notes: string;
    }[];
    files_forbidden: string[];
    issue_url?: string;
  }[];
  merge_order?: string[];
}

interface SequentialNode {
  id: string;
  name: string;
  blocked_by: string[];
  reason: string;
}
```

### 11.3 Conflict Classification Policy

In V2, conflict classification is done at planning time and may be persisted only as notes.

Suggested policy:

- `trivial`: barrel exports, generated indexes, one-line registrations
- `additive`: independent cases/sections in the same file
- `semantic`: same function, same control path, same domain logic
- `unknown`: overlap exists but confidence is not high enough

`unknown` should be treated conservatively, usually as "do not group automatically."

### 11.4 Repo and Resource Awareness

Parallel groups should be partitioned by repo first and by overlap second.

The planner should also emit a validation policy such as:

- max 1 Node-heavy validation task at a time
- allow lightweight static inspection in parallel
- merge additive groups in an explicit order

This keeps the machine safe even when coding work runs in parallel.

## 12. Work Dispatch

For each node in a parallel group:

1. create repo-appropriate worktree
2. create feature branch
3. invoke `setup-work`
4. launch agent with:
   - issue context
   - predicted file ownership
   - forbidden file list
   - validation limits
5. mark `state = 'in_progress'`
6. record `branch`

Example constraint block:

```text
You are working on: sr#586

Files you own:
- packages/viewfinder/src/pages/Modelling/individuals/IndividualAspectForm.tsx
- packages/clarity2/src/domains/aspect/individual/aspect-individual.writer.ts
- packages/clarity2/src/domains/aspect/individual/aspect-individual.reader.ts

Shared files:
- packages/viewfinder/src/hooks/useClarity2Modelling.ts
  Rule: modify only the individual-aspect branch/case

Do not touch:
- packages/viewfinder/src/pages/Modelling/individuals/IndividualRoleForm.tsx
- packages/viewfinder/src/pages/Modelling/individuals/IndividualOccurrenceForm.tsx
```

## 13. Completion, Recheck, and Archive Sync

### 13.1 Completion Flow

Trigger:

- PR merged
- user marks work done
- orchestrator sees branch finished and archived

### 13.2 Sync Steps

1. set `state = 'done'`
2. populate `actual_files`
3. read archive location produced by `archive-work`
4. set `archive_path`
5. clear stale ambiguity metadata
6. recompute frontier

### 13.3 Archive Integration Contract

The manifest expects `archive-work` to remain the owner of:

- archive directory creation
- archive `README.md`
- root `INDEX.md`
- session-log conversion and movement

The manifest only records the resulting path.

This avoids the failure mode where the manifest says work was archived but Escapement's actual archive tree says otherwise.

### 13.4 Recheck Flow

`manifest-check` should:

1. identify stale `in_progress` items
2. reconcile predicted vs actual files
3. ingest newly filed issues
4. re-run overlap analysis
5. prepare additional write-back payloads

Repeated drift in the same files should be recorded in `meta` and used to make future planning more conservative.

## 14. Archive Provenance in V2

### 14.1 Why No Archive Entities

Archive entities are unnecessary in MVP because Escapement already gives us:

- a filesystem path
- a README summary
- a root index row

That is enough to answer the important question:

"Where is the work history for this item?"

### 14.2 Provenance Query Pattern

1. query manifest for `archive_path`
2. read `{archive_path}/README.md`
3. if cross-project browsing is needed, read `{context-path}/INDEX.md`

### 14.3 When to Introduce a Separate Archive Table

Only add manifest-level archive records later if at least one of these becomes necessary:

1. multiple archive snapshots per work item become common
2. archive search must work without touching the filesystem
3. archive metadata needs relational joins independent of work items

If that happens, prefer a dedicated `archives` table over generic graph entities.

## 17. Summary of V2 Changes

Compared to V1, this version:

- removes `unlocks`
- removes `conflicts_with` and `parallel_safe_with` as canonical graph edges
- removes file entities and `touches_file` triples from MVP
- removes archive entities and `archived_at` triples from MVP
- renames the main lifecycle field to execution-oriented `state`
- treats archive provenance as a path reference into Escapement's existing context-path system
- treats overlap classification as planner output, not durable graph truth

This keeps the model closer to the real problem:

`What work exists, what depends on what, what can run now, and where is the resulting work history?`
