Escapement · design document

The Factory

Turning Escapement from a workflow the operator drives step by step into one that can carry an issue to a validated pull request on its own, and earns more autonomy only with evidence.

revision r3.2 status settled for first release captured 2026-11-15 tracking #66

Planning produces a contract. Validation checks one exact revision against it.

If setup-work pairs every acceptance criterion with the evidence that will show it is met, "done" stops being a feeling. The operator approves the plan and holds the merge. Everything between those two touches is run, checked and recorded.

This page restates docs/FACTORY_DESIGN.md for reading. Section references like md §4.1 point back to that file, which stays the source of truth. Design review should target things that would make the first release unbuildable, unsafe or misleading; further rigor comes from running the slice (build step 9).

1 · Why md §1

Today, the operator is the validation system

Escapement already runs a sequential workflow (setup-work → do-work ⇄ commit-changes → create-pr → review-pr → archive-work) and a manifest that plans parallel work over a dependency graph. Planning, atomic commits, archives and dispatch work well. What's missing is any check that doesn't route through a person's judgment in the moment.

Gaps and what answers them
Today

"Done" is subjective. do-work finishes when the scratchpad boxes are ticked.

→
Factory

Each criterion carries evidence that a runner executes and records (§4).

Today

Standards are invented after the fact. Review judges against whatever "done" means at that moment.

→
Factory

The contract fixes the standard at plan approval, before any code exists.

Today

Review isn't independent. review-pr shares the implementer's context and blind spots.

→
Factory

A fresh-context reviewer reads a frozen snapshot and must answer every required question (§6).

Today

Plans are approved, not challenged.

→
Factory

One round of plan critique, right after the first release (§9).

Today

Every step stops for a confirmation, so nothing moves while the operator is away.

→
Factory

Approving the plan issues a run authorization that lets those steps proceed (§3).

What a contract does not prove. It makes validation auditable. It doesn't show that the specification or its tests are adequate. Planner, critic and reviewer can share the same misreading of an issue. Plan approval is the check on the contract, and defects found later are the only signal that it was wrong.

Guiding principles

1Earn autonomy with data. Gates start strict and loosen only on pre-declared evidence.
2A report is about one revision. Results are bound to the exact code, contract, target and policy they checked.
3Guarantees live in code, judgment lives in agents. A deterministic runner owns locks, deadlines, cleanup and reports. Skills orchestrate; agents judge.
4Separate authorship. Fresh-context agents review plans and code. Hiding files by location is a weak boundary and is described as one.
5Bounded by count and by time, and honest about which bounds are enforced. Agent time and tokens are advisory until something can enforce them.
6Agents judge; code checks the judgment is complete.
7Respect machine limits. Builds and tests are serialized machine-wide; the operator's machine freezes under parallel Node load.
8Capture metrics from day one, with enough identity to attribute outcomes later.
2 · Shape & scope md §1.3, §2

Three loops, built one slice at a time

The long-term shape has three loops. The first release builds a thin vertical slice through all of them: one issue, started by the operator, with the operator holding the merge.

    Plan approval becomes a run authorization

    Approval records the contract's digest and issues an authorization scoped to one repo, branch, target and contract. Skills check for a matching active authorization before skipping their confirmations. Without one, they behave exactly as today.

    AuthorizesNever authorizes
    commitpush_branchopen_prrun_validation
    mergeforce_pushcontract_changepush_other_branches

    An authorization ends when the run reaches a terminal state. factory revoke or any contract change revokes it; re-approval issues a new one on the same run.

    As built (#63): setup-work takes this path only when the project's required checks are configured (a settings-only factory check is ready), and then offers Approve + authorize run next to plain Approve, which creates no run. The contract is drafted in the scratchpad, so a rejected plan leaves nothing behind. On approval it checks out the branch (factory start refuses the target branch), excludes its working files with factory exclude, starts the run, writes the contract into the run, checks and approves it, and confirms the authorization's digest matches the stored contract. Readiness is mirrored into the manifest with manifest.sh readiness, under its own key so dependency ambiguities are kept.

    As built (#64): skills ask one question, factory authorization: does this worktree's run match on repo, branch, active authorization, contract.json digest, a non-halted state and the deadline? It answers with what the authorization allows and where to pick up (implement, resume, review, pr, refresh_pr), and never changes anything. commit-changes, create-pr and do-work drop their confirmations only on a match. Under an authorization the factory's work shows as the AI agent's: commits carry its name and email, and the push and PR run as its GitHub account.

    What setup-work adds

    StepWhat it doesWhen
    Readiness checkAre criteria present or derivable? Open questions about intent, scope or dependencies? Returns ready or needs_human with specific questions. A criterion that can't be given evidence is a readiness failure.first
    Context gatheringRelevant PROJECT_LORE entries, archives of related work, similar implementations.first light

    Two risk tiers

    TierMeansEffect in the first release
    standardEverything not sensitive.The gate may later recommend auto-merge if the run is clean.
    sensitiveThe diff touches project sensitive-paths, changes execution policy, or covers migrations, auth, money, public API or architecture.The gate never recommends auto-merge. The reviewer must sign off each sensitive path.

    The tier is proposed at planning and recomputed from the actual diff during validation; the higher one wins. In repos where markdown controls behavior, that markdown is sensitive. For Escapement: skills/**, agents/**, hooks/**, CLAUDE.md.

    4 · The contract md §5

    Criteria, each with its evidence

    The contract is where planning and validation meet. Every evidence item gets two separate judgments: whether it executed and passed, decided by the runner, and whether it actually supports the criterion, decided by the reviewer. Both appear in the report.

    Evidence typeSpecified byResult
    testA selector (file plus test name or pattern), optional cwd and timeout.Resolved from structured results: passed, failed, skipped or not_found. Skipped and not_found count as failure.
    commandA command, cwd, timeout, expected exit code, optional stdout patterns.Exit code, pattern results, log path.
    manualInstructions for a person.pending_manual until someone records an outcome.
    Example: issue #42, expired refresh tokensAttempt 2 of the run, after review

    A contract names no commands: every check comes from project settings, so it can't skip or narrow required-checks. A narrowed verify for quick feedback returns with the fix loop. Changing the contract means re-approval: a new digest and a new authorization on the same run.

    The contract, report, verdict and readiness documents have published JSON Schemas in schemas/factory/, and the runner validates against those same files.

    Contract JSON (md §5.2)
    
      
    Report JSON (md §5.3)
    
        
    evidence_digest hashes the normalized failure output, so the fix loop can tell "same test, different failure" from "no change".
    

      
    Outcomes
    
      
    
        
          
    passAll phases passed; the reviewer found nothing blocking.
    
          
    failA check failed or the reviewer found something blocking. The implementer can act on it.
    
          
    blockedCan't validate: dirty tree, contract mismatch, inactive authorization, missing configuration.
    
          
    errorInfrastructure: crash, deadline, lock wait exceeded, checks modified the tree.

    Manual evidence is recorded with factory record-manual <run> <evidence> pass|fail --note …. Each record is bound to the current report's revision and contract; a new commit invalidates it. When every manual item passes, the outcome moves from pending_manual to pass as a new report revision, and the original is kept. As built (#62): a pending_manual outcome moves the run to validated, so the PR can open while manual items are outstanding.
    
      
    As built (#64): a revision is attempts/{n}/report.r{k}.json with revision, supersedes and manual_outcomes. A single fail resolves the report at once, adds a blocking finding manual:{id} and escalates the run. The result says when the open PR needs factory pr to refresh its report section.
    
    
    

    
    
    
      
    5 · Validation md §4.2–§4.6
    
      
    A report is about one revision
    
      
    factory validate requires the worktree lock, a clean tree, a contract that matches the approved digest, an active authorization and an unexpired deadline. It captures HEAD before checks run, and verifies after checks, at review and at PR time that the tree is still clean and HEAD hasn't moved. A clean tree alone doesn't prove identity: a checkout can change HEAD and leave the tree clean.
    

      
    
        
    What does a report still describe?Change something and see
    
        
    
          
    
          
    
            
            
            
            
            
          
    
          
    
        
    
      
    

      
    Phases
    
      
    
        
    #PhaseWhat it producesWho
    
        
          
    1staticTypecheck, lint, format. Edits to forbidden files. Predicted-versus-actual drift (warning). Test and policy change classification.Runner
    
          
    2evidenceOne structured run of verify, plus any command evidence. Each evidence item is resolved from that run.Runner
    
          
    3reviewOne fresh-context reviewer over a fixed bundle; the runner enforces completeness.Agent
    
          
    4scenariosHidden scenarios.later
    
            
      
    
      
    Deterministic phases stop at the first failure. Tests run once, with structured output (usually JUnit XML). A selector that matches no executed test is not_found, and that's a failure.
    

      
    Results must provably come from this run
    
      
      
        
    • Every invocation gets a new, empty results directory, passed to the command as FACTORY_RESULTS_DIR.
      • 
        
    • Results must be newly created. A stale file from a previous run can't produce a pass.
      • 
        
    • A zero exit with missing results, or results that report zero executed tests, is an error, never a pass.
      • 
        
    • Each results file is recorded with its digest, invocation and command.
      • 
      
    
      
    As built (#61): a failed precondition, such as a stray untracked scratchpad, is blocked before any attempt exists: no attempt is used and the run keeps its state, so the host can add the file to .git/info/exclude and retry. Each report lists its invocations, binding every log and results file (with its digest) to its command. A test that verify doesn't run is not_found: contracts name no commands, so the runner can't run one test on its own yet. See docs/FACTORY_CLI.md.
    

      
    Where run artifacts live
    
      
    Nothing the runner writes goes into the worktree, so validation can demand a clean tree and committing never changes what a report describes. Scratchpads, session logs and constraint files are hidden through .git/info/exclude, without touching the project's .gitignore.
    
      
    As built (#59): --artifact-dir {dir} gives {dir}/{run_id}/. With no context-path, artifacts go in the main checkout at .escapement/runs/{branch}/{run_id}/, which factory start adds to .git/info/exclude.
    
      
    {context-path}/{branch}/runs/{run_id}/
  contract.json               approved contract; the implementer reads it here
  attempts/{n}/report.json    per-attempt report, append-only
  attempts/{n}/logs/…         full command logs
  attempts/{n}/results/…      structured test results
  attempts/{n}/review/        the reviewer's bundle: diff, issue, read-only snapshot at head_sha
  attempts/{n}/review.json    the reviewer's verdict
    

      
    Test and policy changes are classified, not banned
    
      
    The baseline is the merge base: the tests and validation-files as they were where the branch split off. Validation classifies every change in the full diff against it.
    
      
    As built (#61): the baseline isn't stored at approval. validate reads it from git, so a rebase is classified against the new merge base. Test files are those matching the new test-files setting, or named by a contract selector. The patterns are read at both revisions, so a branch can't hide a change by editing the pattern that would catch it. Only a hunk that purely adds a new test block counts as new evidence.
    
      
    
        
    ChangeClassTreatment
    
        
          
    New test file, or new cases in a new blocknew evidenceNormal. The reviewer checks it against the criteria.
    
          
    An existing assertion changed, removed, skipped or loosenedmodified assertionFlagged. The reviewer must justify each one. Blocks an auto-merge recommendation.
    
          
    Anything ambiguous between the twomodified assertionAmbiguity defaults to the stricter class.
    
          
    Test or lint config, scripts, CI; a weakened required checkexecution policyThe whole run becomes sensitive.
    
            
      
    
      
    These measures make tampering visible, not impossible. An agent with shell access can read the context directory and the database. After phase 1 the tier is recomputed from the actual diff, and a sensitive touch makes the run sensitive whatever the plan said.
    
    
    

    
    
    
      
    6 · The reviewer md §4.9
    
      
    The agent judges; the runner checks the judgment is complete
    
      
    factory review-input hands a fresh-context reviewer a fixed bundle: the issue, the approved contract, the exact diff, the draft report, paths to the full logs, and a read-only git archive snapshot at head_sha with its digest. The reviewer reads the snapshot, not the live worktree, because the worktree lock is released between CLI calls.
    
      
    As built (#62): the bundle is written to attempts/{n}/review/. The issue text comes only from the host's --issue-file. Execution-policy changes need a sign-off, just as sensitive paths do. A rejected verdict changes nothing. An accepted one is stored as review.json, and report.json becomes the final report; the draft is kept beside it. The reviewer is a prompt in prompts/factory/ plus the verdict schema, so any runtime can run it. The Claude Code agent only wraps that prompt.
    
      
    The verdict goes back through factory record-review, which refuses anything incomplete. Try it below. The example run touched a sensitive path and modified one existing assertion.
    
      
    
        
    Verdict checkerFill in the verdict the way a reviewer would
    
        
    
          
    
          
    
        
    
      
    
      
    Recording the same verdict twice (by digest) is a no-op. A different verdict for an attempt that is already complete is rejected. Any command the reviewer launches goes through factory exec.
    
    
    

    
    
    
      
    7 · Runner guarantees md §4.1
    
      
    Instructions can't hold a lock. Code can.
    
      
    factory is a small deterministic CLI next to the manifest CLI, sharing its SQLite database. Skills call it; agents never reimplement what it does.
    
      
    
        
    CommandDoes
    
        
          
    start <issue>Creates the run and its artifact directory. State planned.
    
          
    approve <run>Records contract digest and authorization; sets the deadline. State approved.
    
          
    exec <run> -- <cmd>Runs a build or test command under the lock, with a deadline and process-group cleanup; logs to the artifact directory.
    
          
    validate <run>Allocates an attempt, runs the deterministic phases, writes the draft report.
    
          
    review-input / record-reviewIssues the reviewer bundle; checks and records the verdict, then finalizes the report.
    
          
    record-manualRecords a person's outcome for manual evidence, bound to revision and contract.
    
          
    pr <run>Creates or updates the PR idempotently, with the report summary.
    
          
    status / resume / revokeShows state; reconciles an interrupted run; ends an authorization.
    
            
      
    

      
    One build at a time, machine-wide
    
      
    A build lock shared by every worktree serializes every build and test, with a lock-wait deadline. A second, per-worktree lock allows one factory operation per worktree, held through validate, record-review and pr; its holder is recorded so resume can tell a live owner from a dead one.
    
      
    As built (#59): both locks are rows in a factory_locks table rather than flocks. Node has no flock, and the holder has to be in the database anyway. A holder whose process is gone, or whose pid has been reused, is taken over by the next caller. Since the database is per user, the build lock is per user. See docs/FACTORY_CLI.md.
    
      
    
        
    Three worktrees asking to run tests at onceminutes
    
        
    
      
    
      
    The implementer is told to run builds and tests through factory exec so they queue too. An optional PreToolUse hook can reject direct calls to the project's verify or static commands; it ships off.
    
      
    As built (#64): the hook is registered for every project but acts only where the runner keeps its marker, inside the worktree's git directory while a run is approved, implementing or validating under an active authorization. It is on by default during runs (exec-hook: off opts out) and costs one jq and one git call elsewhere.
    

      
    Deadlines bound runner activity, not bookkeeping
    
      
    Each command has a timeout; on expiry the runner kills the whole process group, records error and releases its locks. Approval also stores an absolute deadline_at. Past it, commands that start execution refuse and the run escalates. Bookkeeping stays available.
    
      
    
        
    Commands after the run deadline
          
    
        
    
      
    
      
    Agent wall-clock and tokens are recorded per phase and reported against run-budget, but not enforced in the first release. Reports and logs are written to a temp file and renamed.
    
    
    

    
    
    
      
    8 · States & recovery md §4.7, §4.8
    
      
    Interrupted runs resume without repeating or corrupting work
    
      
    Attempts are allocated atomically (UNIQUE(run_id, attempt)) and inserted before any command runs. Each attempt moves through explicit states, and each transition records its owning process. When resume finds an attempt that didn't finish, the state tells it what happened.
    
      
    
        
    Crash it, then resumePick where the crash happens
    
        
    
          
    
          
    
          
    
        
    
      
    
      
    Budgets survive recovery: resume never resets attempt counts, deadlines or recorded time.
    
      
    PR creation is idempotent
    
      
    factory pr first looks for an open PR on the branch. If one exists it records the number and updates the body; otherwise it creates one and records it in the same step. A crash between creating and recording is reconciled on resume by the same lookup. It holds the worktree lock and re-checks that the branch head still equals the report's head_sha.
    
      
    As built (#64): gh runs as the AI agent's GitHub identity (ESCAPEMENT_AGENT_GH_TOKEN; without it the runner refuses, never acting as the operator), and the runner pushes only HEAD to the run's branch, never forced. The host writes the narrative; the runner appends its report section between markers and replaces only that on updates. Recovery is running factory pr again: the lookup finds a PR an earlier call created. Everything the factory writes to GitHub goes through the runner as the agent.
    
    
    

    
    
    
      
    9 · Fix loop & gate md §6
    
      
    After the first release
    
      
    Bounded fix loop next
    
      
    On fail, the implementer gets the findings only, fixes, commits and re-validates.
    
      
      
        
    • Caps: max attempts (default 3) and the run budget. Exhausted means escalated.
      • 
        
    • Stuck: a blocking finding whose evidence_digest is unchanged across two consecutive attempts escalates. The same finding with changing evidence counts as progress.
      • 
        
    • Regression: evidence that passed before and now fails is flagged.
      • 
        
    • blocked and error always escalate. They aren't the implementer's to fix blindly.
      • 
        
    • Narrowed verify between attempts: a contract may name a faster narrow_verify so fix attempts get quick feedback. It never replaces a required check: the attempt that can produce pass runs every required check in full. Deferred from the first release (#60), where validation runs once per attempt and verify is required by default, so it would never run.
      • 
      
    
      
    Gate next, report-only
    
      
    The gate computes and records a recommendation, and in report-only mode always pings anyway. Toggle the conditions to see what it would recommend.
    
      
    
        
    Gate recommendationAll must hold for auto-merge
    
        
    
          
    
          
    
        
    
      
    
      
    Before an enforcing gate (later). Branch validation can pass while the merge fails. Enforcing needs merge-result validation (validate head_sha merged into the current target), conditional merge (merge only if both SHAs are unchanged), and the promotion criteria in §10.
    
    
    

    
    
    
      
    10 · Metrics md §7
    
      
    Starting the trust record
    
      
    Four tables in the shared manifest database, added by schema migration 2 (#59), plus a fifth, factory_locks, for the runner's locks. Every row carries enough identity (run, revision, contract, policy version) to attribute outcomes later.
    
      
    
        
    TableOne row perKey fields
    
        
          
    factory_runsrunrepo, worktree, branch, target, deadline, state, proposed and actual tier, contract digest, policy version, gate recommendation, operator action, PR, merge SHA
    
          
    factory_authorizationsrun × contractbaseline, what it authorizes, status (active, ended, revoked, superseded)
    
          
    factory_attemptsrun × attemptstatus, owner, verdict digest, outcome, head and target SHA, failed phase, findings, flags, duration, tokens
    
          
    factory_eventseventreadiness, critique finding, state change, gate, operator action, manual outcome, defect, revert
    
            
      
    
      
    Full SQL (md §7.1)
    
      
    Questions it answers, all segmented by policy version: which phase fails, by work type and tier; attempts and cost to converge; which critique findings were accepted and what they changed; how often the proposed tier was right; interruption and error rates.
    
      
    Event conventions. critique_finding records the finding, severity, whether it was accepted and what plan change it caused, so the critic's value is measured directly. defect links a later bug to a run or merge SHA and records how it was attributed. revert links a revert to a merge SHA.
    
      
    The number that unlocks autonomy
    
      
    Agreement between gate and operator isn't enough. The key metric is the false auto-merge rate: auto-merge recommendations later followed by requested changes, rejection, a revert, or an attributed defect. Before any cohort is evaluated for promotion, a short pre-registration note fixes the cohort, the observation window, the acceptable rate and how small samples are handled, and how eligible runs are independently audited. With one operator, cohorts will stay small for a long time, and that's acceptable.
    
    
    

    
    
    
      
    11 · Configuration md §8
    
      
    Per-project settings
    
      
    These extend ## Escapement Settings in each project's CLAUDE.md. All keys are optional; a missing static or verify makes validation blocked ("not configured").
    
      
    
        
    KeyExamplePurpose
    
        
      
    
      
    Settings are read from the run's worktree CLAUDE.md whenever they're needed, not copied per run. Each report records their digest, and a branch that changes them is an execution-policy change, so a weakened setting is flagged for review rather than silently used.
    
      
    If a test runner can only write to a fixed path in the worktree, that path must be gitignored; the runner clears it before each run and moves the results into the artifact directory afterward.

      13 · Risks & open questions md §11, §12
      
      
      Accepted for the first release
      
      
        
        
      • Using factory exec is instruction-based; the hook, on during runs, catches only the project's own static and verify commands.
        • 
        
      • "New versus modified" test classification is a heuristic; ambiguity takes the stricter class.
        • 
        
      • Branch validation can pass while the merge fails. The report says so, and the operator merges.
        • 
        
      • Stale ignored build output isn't detected; projects own clean-build-safe commands.
        • 
        
      • Run artifacts are hidden from git, not from the agent.
        • 
        
      • Agent wall-clock and token budgets are reported, not enforced; the run deadline bounds only runner activity.
        • 
        
      • The contract and its tests may themselves be inadequate. Only plan approval and later defect attribution check that.
        • 
      
      
      
      Still open
      
      
      
        
      Critic diversityDifferent framing or a different model? A/B once critique events exist.
      
        
      Mid-build contract amendmentsEscalate only, or allow a critic-approved amendment within the same run?
      
        
      Reviewer vs. /code-reviewReuse it inside the review phase, or keep a narrower contract-aware reviewer?
      
        
      Work-type taxonomyFrom labels, the plan, or the diff?
      
        
      Non-test evidenceUI, performance, docs: where is manual the honest answer?
      
        
      Runner locationExtend the TypeScript manifest CLI (shared database, existing tooling) or a separate package. Default: extend.
